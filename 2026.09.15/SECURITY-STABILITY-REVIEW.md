# 보안·안정성 검토 — 2026-09-15

## 범위와 한계

2026.09.15 새 홈페이지 및 홈페이지에서 연결하는 워크숍 원본을 검토했다. 소스 정적 분석과 외부 통신을 차단한 별도 Chrome에서 실제 함수 코드를 실행하는 모의 응답 검증을 수행했다. 운영 사이트, Apps Script 서버, 실제 라이선스·API 키는 검증하지 않았다. 운영 서버 공격이나 문의·메일·AI 요청은 수행하지 않았다. 아래 진단 항목은 수정 전 상태를 기록한다. 보완 후 상태는 다음 절을 기준으로 판단한다. 기존 위치의 줄 번호는 수정으로 달라질 수 있다.


## 보완 결과

- **외부 입력 표시:** 포털 결과는 DOM API와 textContent로 구성하고 이벤트 리스너로 연결했다. 문서 이름과 확인된 오류 출력 경로는 이스케이프 또는 textContent로 처리했다. 원본과 난독화 배포본에서 악성 HTML 모의 입력이 실행되지 않고 일반 텍스트로 표시됨을 확인했다. 모든 동적 HTML 경로의 안전성을 보증하는 전수 감사는 아니다.
- **자료 저장 안정성:** REST·포털 자료를 content 필드로 통일했다. 기존 text 필드 자료도 복원 시 정규화하고 잘못된 항목을 처리한다. 실제 목록 렌더링과 기존 자료 복원을 검증했다.
- **요청 종료:** 외부 자료·라이선스 조회에 제한 시간과 HTTP 오류 처리를 적용했다. OpenAI 요청에는 기존 AbortController의 signal을 연결하고 타이머를 정리한다. 문의 요청은 30초 후 중단하고 버튼을 다시 활성화한다.
- **문의 입력 보존:** 요청 완료 시 모달을 닫되 입력은 유지하고, 접수 여부를 확인하지 못했다는 안내를 표시한다. 오류·시간 초과에도 입력이 남는다. no-cors 연동은 유지하므로 실제 접수 성공 확인은 아직 해결되지 않았다.
- **키·라이선스:** 저장한 API 키를 명시적으로 지우는 버튼을 추가했다. 라이선스 캐시의 잘못된 만료일과 비정상 재검증 시간을 검사한다. 클라이언트 캐시는 여전히 인증 근거가 될 수 없다.
- **화면 복구:** 캔버스 엔진 로딩 실패 시 도면 설명·오브젝트 설명을 표시하고 사용 불가능한 캔버스 버튼을 비활성화한다.
- **탐색 안정성:** 언어 전환 후 지연된 글꼴 위치 보정이 이후 사용자의 이동을 덮어쓰지 않도록 취소 조건을 추가했다.
- **배포 구성:** scripts/build-release.mjs가 공개용 파일만 별도 tmp/release-* 폴더로 모은다. 작업 원본 HTML·보고서·테스트·빌드 스크립트는 제외한다. 실제 배포는 수행하지 않았다.
- **리퍼러:** 홈페이지와 워크숍에 strict-origin-when-cross-origin을 지정했다.

### 검증 범위

원본·난독화본의 포털 결과/문서/오류 표시, 정상 자료 로드, 이전 데이터 복원, 요청 시간 초과, 키 제거를 모의 응답으로 검증했다. 문의는 정상 요청·오류·시간 초과에 따른 입력 보존과 버튼 복구를 확인했다. 엔진 실패 시 한영 대체 설명, 한영 전환 위치 보존, 섹션 이동과 모바일 표시도 브라우저에서 확인했다. 배포 후보의 한영 홈페이지와 워크숍이 초기 실행되며 필수 리소스 누락과 런타임 오류가 없음을 확인했다. 브라우저가 자동 요청하는 선택적 favicon.ico의 404는 기능 리소스 검사에서 제외했다. 실제 문의·AI 호출·운영 서버 변경은 하지 않았다.

### 서버 작업이 남은 항목

1. 문의 서버의 CORS 또는 동일 출처 접수 API, 접수 성공 응답, 서버 입력 검증·스팸/요청 빈도 제한.
2. 보호할 데이터·연산에 대한 서버 측 라이선스 검증. 브라우저 코드 난독화나 로컬 만료일 검사로 대체할 수 없다.
3. 실제 호스팅의 HTTPS·보안 헤더·공개 경로 설정. 인라인 스크립트와 기존 연동을 막을 수 있는 엄격한 CSP/COOP는 일괄 강제하지 않았다. 운영 환경에서 호환성을 확인한 뒤 단계적으로 적용해야 한다.
4. 나머지 동적 HTML 출력과 외부 라이브러리의 추가 감사. 이번 보완을 전체 취약점 부재나 운영 보안 검증 완료로 해석해서는 안 된다.

## 최초 진단 — 우선순위

### P1-1. 워크숍의 외부 응답·파일명을 HTML로 직접 삽입

- 위치: nia-worflogy-tool.html:17793–17803 (searchPortal), 11768–11774 (renderDocList), 11062–11066 (연결 테스트 결과).
- 외부 검색 결과 title/orgnNm, 문서 이름, 오류 메시지가 HTML 문자열에 들어간다. 일부 다른 화면에서 이스케이프를 하더라도 이 경로에는 적용되지 않는다.
- 재현: 원본 searchPortal 함수를 로컬 테스트 페이지에서 실행하고 모의 응답의 제목에 무해한 이벤트 핸들러를 포함했다. 브라우저 내 테스트 플래그가 바뀌어 스크립트 실행을 확인했다. 외부 네트워크와 실제 키 사용은 차단했다.
- 영향: 제어 가능한 응답·문서 데이터가 이 경로에 들어오면 DOM XSS로 이어질 수 있다. 동일 출처의 sessionStorage API 키와 작업 데이터에도 접근할 수 있는 위험이다. 실제 외부 API가 공격자 입력을 전달하는 조건은 별도 확인이 필요하다.
- 조치: 텍스트는 textContent, 속성은 DOM API로 설정. 인라인 onclick에 JSON을 삽입하지 말고 addEventListener의 클로저로 연결. HTML이 꼭 필요한 응답에만 검증된 정화기를 적용. 오류 메시지도 텍스트로 출력.
- 원본 수정 후 난독화 배포본도 재생성·동작 검증할 것.

### P1-2. 문의의 접수 여부를 확인하지 않고 입력 초기화

- 위치: js/contact.js:20–29.
- fetch의 no-cors 응답은 opaque여서 상태와 본문을 읽을 수 없다. 현재는 요청 Promise가 해결되기만 하면 form.reset과 dialog.close를 실행한다.
- 재현: 접수 확인이 없는 opaque 모의 응답에서 입력 초기화와 모달 닫힘을 확인했다. 실제 서버가 실패했다는 주장은 아니다.
- 영향: 방문자는 접수된 것으로 받아들일 수 있지만 서버 오류를 감지하지 못하고 입력 내용을 잃는다.
- 조치: CORS가 설정된 접수 API 또는 동일 출처 서버를 두고 접수 성공 JSON/접수 번호를 확인한 뒤 닫기. 실패 시 내용 유지. UI 문구만 바꾸거나 no-cors를 단순 삭제하는 것으로 해결되지 않는다.
- 서버 측 입력 검증·스팸/요청 빈도 제한은 클라이언트에서 확인할 수 없어 별도 검토 필요. 공개 API 주소 자체를 비밀키로 취급해서는 안 된다.

### P1-3. REST·포털 데이터의 저장 필드 불일치

- 위치: nia-worflogy-tool.html:17758–17766, 17808–17812; 소비 측 11772, 11184.
- 해당 로더는 {name,text}를 저장하지만 문서 목록은 d.content.length를 읽고, 문맥 계산도 content를 읽는다.
- 재현: 실제 fetchApiData 함수에 모의 JSON 응답을 전달한 결과 text만 있고 content가 없음을 확인했다. 후속 렌더링은 테스트에서 대체했으며, 실제 renderDocList의 content.length 접근은 소스로 확인했다.
- 영향: REST 자료 로드 뒤 목록 렌더링 예외, 문맥 누락, 저장된 잘못된 데이터의 재로드 실패 가능.
- 조치: 문서 모델을 {name,content,category}로 통일하고 모든 가져오기/저장/복원 경계에서 검증. 기존 text 자료는 content로 마이그레이션.

### P2-1. 라이선스 UI가 브라우저 저장값을 신뢰

- 위치: nia-worflogy-tool.html:10116–10126, 10178 이후.
- localStorage의 key/expiry/lastCheck로 사용 가능 여부를 판단하고 24시간 간격으로 재검증한다. 이 값은 사용자 측에서 변경 가능하다. 잘못된 날짜 값도 명시적으로 거부하지 않는다.
- 영향: 현재 UI 게이트를 강제적인 이용 권한 통제라고 볼 수 없다. 서버 자원 접근까지 가능한지는 서버 코드를 보지 않아 확인하지 않았다. 난독화는 권한 검증의 대체 수단이 아니다.
- 조치: 유료·제한 서버 기능은 매 요청 서버에서 권한 검증. 오프라인 허용 정책은 별도 정의하고 서명된 라이선스와 검증 가능한 만료 정보 사용. 순수 클라이언트 UI의 우회 방지에는 한계가 있다.

### P2-2. 타임아웃이 없거나 실제 요청에 연결되지 않음

- 위치: js/contact.js:21; nia-worflogy-tool.html:11201–11229, 17744, 17788.
- 문의와 데이터 로드 요청에 앱 차원의 시간 제한이 없다. 워크숍 LLM 함수는 AbortController를 만들지만 OpenAI 요청에는 signal을 넘기지 않는다. Gemini·로컬 요청에는 연결되어 있다.
- 영향: 요청이 오래 멈추면 전송/분석 상태에서 버튼이 비활성화된 채 대기할 수 있다.
- 조치: 각 fetch에 AbortSignal 연결, finally에서 타이머 정리, 취소/재시도 제공. 문의 POST는 중복 접수 방지를 고려하고 무조건 자동 재시도하지 않는다.

### P2-3. 같은 출처에서 실행되는 워크숍과 API 키의 영향 범위

- 위치: nia-worflogy-tool.html:11047–11048; js/main.js:115–123.
- 워크숍은 사용자 API 키를 sessionStorage에 둔다. 별도 탭이어도 같은 출처의 스크립트 신뢰 경계는 분리되지 않는다. opener=null은 역방향 창 조작을 줄이지만 HTML 삽입 취약점 자체를 막지 않는다.
- 조치: P1-1 우선 해결, 키 제거 기능과 보관 범위 명시. 필요 시 워크숍을 별도 출처로 분리하고 서버 중계·짧은 수명의 자격 증명을 검토. 사용자가 직접 제공한 키와 사이트 소유자의 비밀키는 구분해야 한다.

### P2-4. 배포 파일 허용 목록과 보안 헤더 설정 필요

- 폴더에 tmp 테스트 도구, 문서, 난독화 전 HTML, 빌드 스크립트가 함께 있다. gitignore는 tmp를 제외하지만 폴더 통째 업로드를 막지는 않는다. 현재 공개 노출을 확인한 것은 아니다.
- 폴더 내 배포 헤더 설정 파일이나 HTML CSP는 확인되지 않았다. 운영 서버에 이미 설정됐는지는 미확인.
- 조치: 공개 파일만 생성하는 배포 산출물 구성, 디렉터리 목록 비활성화. 서버에서 CSP, frame-ancestors, X-Content-Type-Options, Referrer-Policy와 HTTPS 정책 검토. 홈페이지와 인라인 스크립트가 많은 워크숍에 동일한 엄격 정책을 무작정 적용하면 기능이 깨질 수 있으므로 Report-Only로 먼저 검증.

### P3. 캔버스 실패 시 설명 대체 콘텐츠 보존

- 위치: js/main.js:6, 95 이후.
- 초기 정적 설명을 먼저 비우고 인터랙티브 화면을 구성한다. 렌더러가 실패하면 오류 안내는 있지만 풍부한 정적 설명은 사라진다.
- 조치: 렌더링 성공 뒤 정적 콘텐츠를 대체하거나, 오류 시 해당 섹션의 제목·설명·오브젝트 목록을 복원. 폰트·라이브러리 실패와 저장 공간 접근 거부 상황도 회귀 검사에 포함.

## 잘 되어 있는 부분

- 홈페이지 본문은 주로 textContent로 갱신한다. 정적인 SVG용 innerHTML 자체를 사용자 입력 취약점으로 분류하지 않았다.
- 언론사 링크에 noopener/noreferrer 적용. 워크숍 창도 opener를 끊고 기존 창을 재사용한다.
- 홈페이지 폰트와 핵심 라이브러리는 로컬 파일로 제공한다.
- 문의 필드의 브라우저 검증과 중복 클릭 방지가 있다. 서버 검증의 대체 수단은 아니다.
- 보이지 않는 캔버스의 루프를 멈추는 최적화가 있다.

## 권장 작업 순서

1. 워크숍 HTML 삽입 경로와 문서 모델 불일치 수정.
2. 문의 접수 API의 확인 가능한 응답 설계, 입력 보존과 타임아웃 수정.
3. 라이선스 서버 검증 및 API 키 격리 정책 확인.
4. 배포 허용 목록·보안 헤더·장애 시 대체 표시 적용.
